# The benchmark target

A deliberately hostile application, built to host the corpus in
[docs/en/benchmark/corpus.md](../../docs/en/benchmark/corpus.md). Every defect it can
testence was observed on a real product first — see
[docs/en/benchmark/taxonomy.md](../../docs/en/benchmark/taxonomy.md).

```bash
npm ci --prefix app && npm run build --prefix app   # once: builds ../static
.venv/Scripts/python bench/sut/server.py            # http://127.0.0.1:8800
.venv/Scripts/python bench/sut/verify.py            # 21 checks on the fixture itself
```

## Real-React latency gate

The production bundle is also the maintained speed target. From the repository root:

```bash
.venv/Scripts/python bench/react_latency.py
.venv/Scripts/python bench/react_latency.py --repeats 5 --check
.venv/Scripts/python bench/react_latency.py --shared-browser --repeats 5 --check
.venv/Scripts/python bench/warm_runner_latency.py --repeats 5 --check
```

The first command is a quick local profile. The second starts five fresh pytest
processes and applies the broad ceilings in `bench/budgets/react_latency.json`.
It separates browser/bootstrap cost, navigation and render readiness, controlled
input, exact mutation-response waiting, React commit and the full mutation round
trip. The ceilings are intentionally large enough for different CI hosts: they catch
timeout-shaped regressions, not harmless millisecond noise.

The third command keeps one persistent browser context and makes every fresh pytest
process attach over CDP. It uses a separate budget so launch and attach samples cannot
be mixed accidentally. The launcher cost is reported once and kept outside each run;
this profile represents a repeated agent-authoring loop, not a one-off CI invocation.

The fourth command holds that browser constant and compares fresh pytest processes with
warm pytest sessions that retain their Playwright/CDP engine connection. Its gate covers
runner bootstrap and relative savings only; application latency remains reported but
cannot turn the runner gate red.

The checked-in snapshots are `bench/results/react_latency.json` and
`bench/results/react_latency_attached.json`, plus
`bench/results/warm_runner_latency.json`; local diagnostic outputs should use the
ignored `bench/results/local-*` prefix.

## How a defect is injected

Open the page with the behaviours you want:

```
http://127.0.0.1:8800/?run=item-07&defects=D-40,D-45
```

The client parses that list, applies its own halves, and **echoes it back in an
`X-Defects` header on every API call**, where the server applies its halves. One id,
two layers, one configuration — which is what lets a single flag break the interface
and the API at once. Sixteen of the forty corpus items are defined by exactly that
disagreement, so it is the mechanism, not a convenience.

`defects.json` is the single registry, read by `server.py` and imported by the app.

**An unknown id refuses to run.** Both halves reject it: the server answers 400 and
the client renders an error instead of an application. A corpus item that misspells a
flag must not quietly exercise a healthy product and report a pass — that would be a
false green manufactured by the benchmark itself, which is the one failure mode this
whole exercise exists to measure.

## Isolation

`?run=<id>` selects a store. Runs never see each other's writes.

This was not in the design; the fixture's own verification found it. A case that
created a row moved the baseline for the five cases after it, and they failed against
a total that had been correct a moment earlier — a shared-state hazard reproduced
inside the benchmark's target. Without
isolation the corpus would partly be measuring the order its items ran in. It also
gives a parallel run what it needs: many items times their repeats is not a serial
workload.

## Why this shape

**A Python server in front of a React bundle.** Node builds the bundle once, at
development time. Running the corpus needs only what the framework already needs —
ADR-0007 keeps the runtime dependency surface small, and a benchmark that drags a
node toolchain into every run is a benchmark people stop running.

**Real React, not an imitation of one.** Several items cannot be expressed without
it: D-40 *is* a `useState` guard that swallows the first update, and writing it as
anything else would be measuring a caricature. There is no `<StrictMode>`, on
purpose — it double-invokes effects in development and not in a production build, and
items defined by *how many times* something happens would then behave differently
while being written than while being measured.

**Deterministic data.** 47 rows generated by index from a fixed vocabulary, two of
them soft-deleted from the start. No clock, no randomness: a fixture that varies
between runs hands the benchmark its own flake rate. When a corpus item does need
genuine intermittency, it will come from a seeded generator declared in the registry,
not from ambient `Math.random`.

## What is here so far

Screen 1 of five (**collection**), with nine defects and seven controls wired and
verified. Still to build: the create form in a portal modal, the entity card with
tabs and two concurrent sessions, the wizard, and the long-running operation.

| behaviour | half | what it does |
|---|---|---|
| `D-13` | client | the view does not catch up after a write; a reload fixes it |
| `D-15` | client | placeholders stay forever and satisfy a presence check |
| `D-17` | server | a soft-deleted row is still listed |
| `D-34` | client | a filter in the URL is ignored on a fresh load |
| `D-40` | client | the first parameter change after a load is silently discarded |
| `D-43-short-page` | server | the page returns fewer rows than it reports |
| `D-43-counter` | server | the reported total disagrees with the real one |
| `D-44` | server | search matches by prefix where substring is documented |
| `D-45` | server | the filter reaches the server and does not shape the result |
| `C-08-*` | client | rename · restyle · reorder · wrap — must stay green |
| `C-10` | server | 300 ms added to every response |
| `C-12` | client | a permanent console error that affects no scenario |
| `C-13` | client | search commits only on Enter — inert typing is by design |

Two of these are flagged `retry_hides_it` in the registry, and they are the reason
the corpus exists. **D-40** is cured by the retry a framework performs
automatically; **D-13** is cured by the reload a suite performs between acting and
asserting. Both report green to a tool that does the ordinary thing.

## A note on designing items

`D-43-counter` offsets the reported total by three, not by two. With two it landed
exactly on the count including soft-deleted rows — that is, on `D-17`'s observable
state. **Two defects that produce one identical observation are a corpus defect**:
the set could no longer tell which of them it had seeded. Worth checking for every
new pair.

`D-44` needs its corpus item to choose a search term where the prefix match is a
non-empty subset of the substring match. With a term that prefixes nothing the page
goes empty, and an empty page is a loud failure — which is the opposite of what this
class is for.
