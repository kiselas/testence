# Действия владельца для доведения Testence R1 до RC

Дата: 2026-09-07

Обновление 2026-09-08: владелец разрешил release-ветку и push при сохранении
private visibility. Reference host пока отложен, прогоны выполняются локально.
Codex доступен в текущей сессии, Claude проверит владелец по
[инструкции](agent-client-check.md). [TestOps sandbox](../../../infra/testops-sandbox/README.md)
подготовлен до получения trial/registry access. Ниже исторический полный checklist;
повторно запрашивать уже разрешённые branch/push и reference host не требуется.

Цель этого списка — отделить действия, которые требуют владельца проекта или независимых внешних участников, от работы, которую исполнитель может завершить самостоятельно.

## 1. Одно сообщение для запуска автономной подготовки кандидата

Владелец должен зафиксировать версию и разрешённые внешние действия. Рекомендуемый вариант:

> Подготовь Testence R1 как `0.1.0a1` в ветке `codex/r1-rc`. Проведи полный аудит текущего рабочего дерева, включи все относящиеся к R1 изменения, не включай временные файлы, виртуальные окружения, локальные outputs и секреты. Создай чистый commit, отправь ветку в `kiselas/testence`, запусти hosted CI и исправляй найденные проблемы до зелёной матрицы. Разрешаю клонировать и тестировать два публичных OSS-проекта, использовать предоставленный TestOps sandbox и запускать реальные Codex и Claude workflows. Публикацию в PyPI выполняй только после отдельного финального разрешения.

Если нужна другая версия, заменить `0.1.0a1`. Версия `0.1.0.dev0` подходит для локальной разработки, но не для внешнего RC-кандидата.

Из-за большого текущего рабочего дерева нужно также либо подтвердить, что все относящиеся к Testence изменения можно собрать в кандидат, либо перечислить файлы/изменения, которые принадлежат другой работе и должны быть исключены. Исполнитель сам подготовит и покажет итоговый staged diff перед фиксацией.

## 2. GitHub и PyPI: действия владельца

- Убедиться, что исполнитель может push в `git@github.com:kiselas/testence.git` и запускать GitHub Actions.
- Включить required checks для release-ветки или основной ветки после того, как названия CI jobs станут известны из первого hosted run.
- Включить GitHub Private vulnerability reporting. Значение секретного адреса в чат не передавать; достаточно подтвердить, что канал включён и доступен в Security tab.
- Создать защищённое GitHub Environment с именем `pypi` и назначить владельца обязательным reviewer.
- В PyPI создать Trusted Publisher для пакета `testence`: repository `kiselas/testence`, workflow `publish.yml`, environment `pypi`. API token не нужен и не должен передаваться исполнителю.
- Не подтверждать публикацию заранее. Финальное разрешение даётся только для конкретного commit SHA, tag, hashes артефактов и digest release manifest.

Если интерфейсные настройки GitHub/PyPI владелец хочет делегировать, нужно отдельно разрешить управление ими через браузер в уже авторизованной сессии. Пароли, recovery codes и секреты в чат не отправлять.

## 3. TestOps sandbox

Предоставить непроизводственный tenant и service account с минимальными правами, необходимыми для:

- выбора test plan;
- создания launch;
- загрузки результатов и вложений;
- чтения истории и проверки повторной отправки.

Секреты положить в GitHub Actions secrets или локальное хранилище секретов. Исполнителю сообщить только:

- base URL;
- имена secret variables;
- разрешённый project/test plan;
- ограничения tenant;
- срок действия учётной записи.

Нужны данные для двух реальных выборок: малой (`1/8`) и расширенной (`3/20`), включая pass/fail/broken/skip, retries, history и attachments. Production tenant и реальные чувствительные данные не требуются.

## 4. Два реальных agent-client workflow

Нужно обеспечить доступ к двум отдельным клиентам:

- Codex;
- Claude.

Каждый клиент должен самостоятельно пройти один и тот же зафиксированный workflow на одном candidate digest: установить/проверить managed skill pack, выполнить задачу над demo или OSS target, запустить Testence и получить проверяемый receipt.

Если оба клиента доступны исполнителю через CLI или UI, владелец только подтверждает разрешение их запускать. Если Claude доступен только владельцу, владелец запускает подготовленный исполнителем prompt без изменений и возвращает полный результат/receipt. Два запуска одного клиента не считаются двумя независимыми client workflows.

## 5. Независимые reviewers

Назначить людей, которые не реализовывали проверяемую часть:

| Роль | Минимальный результат |
|---|---|
| Truth reviewer 1 | Проверяет claims, oracle, evidence и ошибки классификации на замороженном кандидате |
| Truth reviewer 2 | Независимо повторяет truth review; не копирует вывод первого |
| Holdout custodian | Хранит 8 holdout cases закрытыми до freeze и выдаёт их только для финального прогона |
| Security reviewer | Проверяет threat model, path/link protections, supply chain, disclosure route и release workflow |
| Rights reviewer | Проверяет лицензии двух OSS targets, fixtures, screenshots/assets, notices, SBOM и право публикации |

Один человек может совмещать security и rights review, если он независим от реализации и подписывает два отдельных scope-bound результата. Два truth review должны оставаться независимыми.

Владелец должен пригласить reviewers в репозиторий или дать им review bundle. Публично достаточно псевдонима/роли, даты, scope digest, решения и замечаний; персональные данные публиковать не нужно. Самопроверка исполнителя и второй AI-agent не заменяют независимый human review.

## 6. Два OSS target

Выбор проектов можно полностью оставить исполнителю. От владельца требуется только сообщить запрещённые лицензии или отрасли, если такие ограничения есть.

Исполнитель выберет два публичных web-проекта с совместимыми лицензиями, зафиксирует полный commit SHA каждого, сохранит license/notice evidence и построит две отдельные воспроизводимые интеграции. Публиковать изменения upstream или открывать PR без отдельного разрешения не требуется.

## 7. Пилот

Владелец должен найти и пригласить:

- 5 новых пользователей;
- из 3 внешних команд;
- одна команда предоставляет одного QA, работающего с 3 проектами;
- одна команда выполняет живой selective launch в TestOps.

Каждый участник использует один и тот же wheel digest и начинает с пустого workspace. Нужно согласие на сбор обезличенных метрик. Не собирать production URLs, секреты, PII и необработанные screenshots.

После первой сессии необходимо организовать возврат участников на следующей календарной неделе. Это обязательная календарная зависимость; заменить её локальным повтором в тот же день нельзя.

Исполнитель подготовит инструкции, session bundle, форму receipt и разберёт результаты. Для рассылки приглашений от имени владельца требуется явное разрешение отправлять сообщения; без него владелец рассылает готовый текст самостоятельно.

## 8. Reference host

Предоставить runner или VM с зафиксированными характеристиками:

- 4 vCPU;
- 8 GiB RAM;
- SSD;
- поддерживаемая Windows или Linux конфигурация.

На нём исполнитель выполнит 30-repeat scale run и привяжет receipt к candidate SHA, wheel hash, OS, Python и browser version. Если обычный GitHub-hosted runner не даёт гарантированных характеристик, использовать self-hosted runner/VM.

## 9. Финальное решение владельца

После завершения hosted matrix, OSS, client, TestOps, reviews, pilots и reference-host run исполнитель сформирует один release bundle и `go` manifest. Владелец сверяет:

- candidate commit SHA и tag;
- wheel/sdist hashes;
- manifest payload digest;
- все обязательные receipts и отсутствие no-go;
- результат независимых reviews;
- готовность disclosure channel и PyPI environment.

После этого владелец даёт отдельное разрешение вида:

> Разрешаю публикацию Testence `0.1.0a1` из commit `<SHA>` и immutable candidate artifacts с manifest payload digest `<DIGEST>` через защищённый workflow `publish.yml` в environment `pypi`.

Без точных SHA и digest это разрешение не считается release approval.

## Минимум информации, который нужен от владельца сейчас

1. Выбранная версия (`0.1.0a1` рекомендуется).
2. Разрешение создать clean branch/commit, push и запустить hosted CI.
3. Подтверждение состава текущего рабочего дерева или список исключений.
4. TestOps sandbox и ссылки на secret names/allowed project.
5. Доступность реальных Codex и Claude clients.
6. Контакты/handles независимых reviewers.
7. Контакты 5 пилотных пользователей из 3 команд и желаемая неделя старта.
8. Доступ к reference runner/VM.
9. Ограничения по лицензиям/тематикам OSS targets, если они есть.

После передачи этих девяти пунктов до финального `go` от владельца потребуется только решать реальные access failures, если они возникнут. Следующая обязательная точка участия — проверка конкретного release bundle и разрешение публикации.
