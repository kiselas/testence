# Автономное выполнение этапа 3

Дополнение от 7 сентября 2026 к [ТЗ](README.md). Предпочтение владельца: максимально завершить работу без его промежуточного участия. Этот документ устанавливает порядок самостоятельных решений исполнителя и не уменьшает G1–G8/R01–R24.

## 1. Что реально можно обещать

ТЗ достаточно подробно для самостоятельного выполнения инженерной части с исследованиями по ходу работы. Не нужно заранее согласовывать каждое имя функции, fixture или library choice. Но ни объём ТЗ, ни passing tests не гарантируют отсутствие ошибок исполнителя: сложные filesystem/transaction/security изменения требуют проверки отрицательными consumers и review.

Один агент не может создать факты независимого человеческого review, три реальные команды пилота или их week-return. Такие критерии выполняются без участия владельца только если необходимые участники, полномочия и доступы уже организованы. В этом дополнении наличие доступов не проверено и не предполагается автоматически.

## 2. Три различимых результата

| Результат | Минимальное содержание | Допустимое название |
|---|---|---|
| Инженерный кандидат | Код/docs/fixtures/negative tests завершены, clean source snapshot и wheel/sdist; остаточные внешние условия перечислены | `engineering_candidate`, release decision `no-go` при неполных gates |
| Технически проверенный RC | Всё выше + фактически пройденная обязательная OS/dependency/hosted CI matrix, artifact binding, corpus/resource checks в требуемом scope | RC с явной таблицей непринятых внешних gates; не «R1 accepted» |
| Полностью принятый R1 | Все исходные G1–G8/R01–R24, реальные reviews/пилоты и owner decision | `R1 accepted`; публикация отдельно в разрешённом scope |

Эти названия не заменяют статусы отдельных receipts. Нельзя пометить задачу `rc_verified`, если есть только локальный Windows запуск. Инженерный кандидат не становится полностью принятым RC изменением заголовка документа.

## 3. Решения, которые исполнитель принимает сам

После поручения реализовать этап агент самостоятельно:

- Выбирает внутренние module/function names, размещение helpers, минимальные необходимые зависимости и структуру fixtures по ТЗ и текущим conventions.
- Фиксирует схемы/CLI syntax/migration в коротком ADR и реализует их; не останавливает работу для согласования обычного design note.
- Выбирает два публичных OSS targets по проверяемым требованиям S3-08, исследует происхождение/лицензии и закрепляет revisions. При технической непригодности заменяет target до freeze, сохранив обоснование. Независимый rights/truth review от этого не становится выполненным.
- Создаёт isolated environments, выполняет browser/negative/consumer tests и разрешённые локальные scans. Применяет уже доступные sanctioned CI/test credentials по их scope, не просит выдать их повторно.
- Выполняет calibration новых budgets по S3-14 и фиксирует protocol до acceptance; не изменяет исходные обязательные пределы для получения green.
- Исправляет найденные при реализации дополнительные дефекты внутри исходного R1 scope, документируя причину и regression. Крупный новый продуктовый scope не добавляет.
- Готовит EN/RU docs, реальную запись synthetic demo, release notes, package manifests и maintainer runbook. Отсутствие готового видео не считается задачей, которую обязательно должен делать владелец.
- Готовит review/tenant/pilot bundles и заполняет всё, что подтверждено инструментами. Не подставляет вымышленные внешние данные.

Правило выбора: сначала существующее подходящее решение проекта, затем самый небольшой поддерживаемый вариант, удовлетворяющий negative tests и Python 3.10/Windows/Linux. Не писать самодельный неполный schema interpreter или небезопасный lock ради отсутствия dependency. Перед новой dependency проверить актуальную первичную документацию, совместимость, лицензию и зафиксировать версию/роль.

Local commits/source candidates готовятся при реализации этапа в рамках поручения на repository work, после проверки diff и intended inputs. Чужие changes не сбрасываются и не включаются в candidate вслепую; при необходимости используется отдельный checkout со снятым snapshot. Push, remote CI dispatch и изменение настроек выполняются только при имеющемся разрешённом remote scope. Отсутствие этого scope не мешает подготовить local candidate и workflow.

## 4. Проверка внешних зависимостей в начале, а не в конце

Во время S3-00 создать `progress.md` и `readiness.md` в каталоге этапа. Это будущие записи исполнителя: сейчас они не заполняются фиктивным PASS.

`readiness.md` содержит для каждой строки статус `available`, `unavailable` или `not_verified`, дату проверки, безопасное evidence и конкретный оставшийся шаг:

| Зависимость | Как проверить без запроса секретов в чат | Что делать, если недоступна |
|---|---|---|
| Windows/Linux/Python/browser matrix | Реальные executable/runner capabilities и минимальный consumer | Завершить доступную matrix, подготовить missing runner job; оставить точный pending check |
| Reference host | Фактические CPU/RAM/storage/runtime характеристики | Локальная calibration отдельно; не назвать другой host reference receipt |
| Git remote/CI permissions | Read-only repository/workflow/auth scope проверки | Готовые commits/artifacts/workflows и команды dispatch; не заявлять hosted pass |
| TestOps test tenant | Наличие разрешённого config/secret reference и read-only connectivity | Полный offline adapter suite и live acceptance bundle |
| Два real-agent clients | Версии, существующая authentication и разрешённые usage limits | Portable skills/contract consumers готовы; actual client checks pending |
| Truth/holdout/security/rights reviewers | Фактические identities, scope и доступный review channel | Подготовленный review bundle; автор не подписывает независимость за других |
| Пилотные участники | Уже согласованные 5 users/3 teams/2 reproductions и канал результатов | Готовый demo/protocol/results form; не симулировать пользователей |
| Security channel/release environment | Read-only проверка реальной repository configuration | Готовые configuration steps и отсутствующие permissions/settings |
| Owner decision | Уже данное решение по конкретному candidate scope | Сформировать exact decision packet после проверки; не присваивать согласие |

При проверках не печатать tokens, cookies, raw `.env`, private participant data или sensitive CI logs. Использовать имеющиеся secret references. Наличие сетевого доступа не означает разрешения на любой внешний write.

Не нужно спрашивать владельца о каждой строке readiness. Первоначально зафиксировать факты и продолжить независимые задачи. Если для следующего шага действительно необходим новый доступ/полномочие, объединить оставшиеся actionable зависимости в один конкретный запрос после подготовки reviewable результата. Не задавать повторно уже отвеченный вопрос.

## 5. Что не считается поводом остановиться

- Не выбран JSON validator, lock primitive, fixture layout или имя schema: самостоятельно выбрать по constraints, проверить и оформить ADR.
- Требуется изменить предложенное внутреннее имя модуля: изменить с сохранением public behavior/acceptance.
- Первый negative test или consumer упал: установить причину, исправить implementation либо setup; не уменьшать assertions.
- На Windows нельзя создать symbolic link: выполнить junction fixture и обязательную Linux symlink matrix доступным разрешённым способом.
- Нет TestOps tenant или reviewer: продолжить все задачи без этой зависимости.
- Выполнены A01–A09: проверить оставшиеся R01–R24, не завершать этап по девяти findings.
- Неизвестна длительность сложной задачи: сделать минимальный design spike и законченный slice; не требовать от пользователя выбрать алгоритм.

## 6. Что нельзя заменить самостоятельным решением

Нельзя придумывать approval, чужой review, внешнюю команду, факт возврата через неделю, remote upload/history или hosted CI run. Второй prompt или повторная самопроверка автора не равны независимому человеческому truth review, предусмотренному S3-08.

Желание владельца избежать промежуточного участия не является разрешением отправлять приглашения, покупать сервисы, публиковать package, открывать private repository или менять production integrations. Использовать уже существующие разрешения; если их нет, подготовить всё до соответствующего внешнего действия. Требование нового разрешения объяснять точным действием и отсутствующим scope, не общей осторожностью.

Нельзя изменить owner decision на `go` только на основании желания «закончить без меня». Решение должно относиться к проверяемому candidate и фактической полноте gates. Если владелец впоследствии задаст явную автоматическую release policy, следовать ей в указанном scope; это не создаёт недостающие pilot/review facts.

## 7. Когда заканчивается автономный проход

Не завершать проход, пока есть невыполненная доступная задача, regression failure без исследования, непроверенный artifact или незаполненный receipt, который можно получить в текущем разрешённом окружении.

Перед handoff проверить:

1. Каждый S3/check ID имеет actual status и ссылку на evidence либо конкретную внешнюю зависимость.
2. Приняты все доступные engineering checks; нет скрытого локального TODO под видом external pending.
3. Существуют проверяемый source candidate, wheel/sdist/checksums, migration/rollback, demo и docs; если какой-то из них не создан, названа реальная причина.
4. Все доступные hosted/consumer checks выполнены на правильных artifacts; старые receipts не выданы за новые.
5. Для непринятых gates готов один `external-handoff.md`: что отсутствует, кто/какой доступ нужен, готовые команды/fixtures, expected outputs и как приложить результат. Без общих фраз «проверьте CI».

Последний ответ указывает достигнутый уровень из раздела 2. Если осталось только внешнее, это законченный автономный engineering pass, но **не полное завершение нынешнего этапа 3**. Полностью завершить его без участия владельца можно при заранее доступных внешних исполнителях и разрешениях; гарантировать это одним ТЗ нельзя.

## 8. Дополнение к стартовому запросу

> Работай автономно по `autonomy.md`: технические решения принимай сам в рамках ТЗ, не останавливайся для обычных согласований. Сначала проверь реальные зависимости, затем доведи все доступные задачи до проверенного результата. Используй уже выданные разрешения без повторных запросов. Не заканчивай после промежуточного milestone. Если остались только недоступные внешние условия, подготовь инженерного кандидата и один конкретный пакет их приёмки; явно назови непринятые gates и не заявляй полного R1 Done.
