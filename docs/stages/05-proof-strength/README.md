# Этап 5. Сила доказательства: оракул из плана и негативное доказательство

Версия плана: **1.0, 26 октября 2026**.
Исходная точка: `main` на `9b4edb2`.
Статус: **в работе**, фаза 1 в PR #49.
Связь с этапом 4: не зависит от него и не блокирует его; фазу 1 можно вести параллельно.

## 1. Откуда взялся план

Разбор демо-репозитория `sMichellin/demo_boost_sdd` (доклад «AI-native тестирование»,
AI BOOST 2026). Его мысль: сгенерированный тест не знает, что такое «правильно»; если
оракулом служит код или текущее поведение, тест закрепляет баг как норму, а зелёный
прогон и 100% покрытия требований достижимы тестами-пустышками. Ловит пустышки только
проверка, что тест умеет падать (там это mutation score по PIT).

Что в Testence уже есть и переносить не нужно:

- спецификация с ID требований: PlanSpec v2, обязательные claim без сценария
  отклоняются (`contracts/plan.py`), verdict сверяет покрытие claim с паком;
- «у каждого требования есть тест»: статус `unverified` и `ci evaluate --quality
  assurance` (`ci.py`), который падает на недоказанных тестах;
- бенчмарк на внесённых дефектах с проверкой «упал нужный claim»:
  `bench/corpus` (`right_reason_rate`), что сильнее их «любой новый красный тест».

Найденная дыра. Шаг 8 `testence-author` и его completion gate требуют сломать тест на
негативном контроле и убедиться, что упал нужный claim; `testing-a-feature.md` раздел 5
учит тому же. Но ledger этого не записывает, `inspect` не показывает, `ci evaluate`
не требует. Тест с привязанным, но бессодержательным assert (сравнение с тем, что
агент увидел при разведке) получает `verified`, и отличить его от настоящего нельзя.
Словарь «negative control» в проекте есть, артефакта нет.

## 2. Решения

1. Берём **дисциплину измерения**, а не гейты как есть: мутировать код приложения в
   браузерных тестах нельзя, и автор демо сам пишет, что его результаты с Java-юнитов
   на E2E не переносятся. Наш аналог мутанта — объявленный негативный контроль
   (инъекция дефекта через `ex.rewrite_response`/`ex.route`, seed с дефектом,
   выключенный обработчик в SUT).
2. Негативное доказательство — **отдельный, более строгий уровень качества**, который
   команда включает сама. Обязательным для всех он не становится: это добавляет прогон
   на каждое требование и бьёт по времени до принятого доказательства (гипотеза H2
   протокола бенчмарка).
3. Формат OpenSpec, PIT, defect escape rate из CSV, теги `step-NN` и бенчмарк на
   патчах для пользователей не берём (раздел 7).
4. Ни один пункт плана не ослабляет существующие гейты и не добавляет ретраи
   (AGENTS.md, CONTRIBUTING).

## 4. Фаза 1. Скиллы и правила (один PR, без изменений рантайма)

### S01. Происхождение ожидаемого значения

Добавить в «Authoring rules» `testence-author/SKILL.md`: ожидаемое значение в любом
`expect_*`, `ExpectedState` и `verify` берётся из поля `expected` сценария PlanSpec или
из данных, которые сам тест создал через seed. Значение, которое текущий UI или API
вернули при разведке (`testence_snapshot`, `explore`, `oracle suggest`), годится для
выбора цели и эндпоинта, но не для assert: это оракул из кода, и он закрепляет баг.
В `proof-gates.md` таблицу «Claim-to-proof review» дополнить вопросом «откуда взято
ожидаемое значение». В `planspec-v2.md` оговорить, что `expected` должно содержать
конкретное значение или правило его вычисления, а не «корректный результат».

Приёмка: правило есть в трёх файлах, `uv run testence agent verify` зелёный.

### S02. Стоп на неоднозначности

В `testence-plan` и `testence-author`: если `expected` или THEN сценария нельзя
превратить в assert без догадки (нет числа, единицы, границы, порядка; слова вроде
«some», «usually», «a while», «быстро», «корректно»), агент не пишет тест, а фиксирует
открытый вопрос с вариантами толкования и останавливается до правки плана человеком.
В plan-скилле это уже есть как «open question»; нужна формулировка с триггерами и
явный запрет писать тест на догадке.

Приёмка: формулировка в обоих скиллах; пример открытого вопроса в `planspec-v2.md`.

### S03. Что нельзя делать ради зелёного

AGENTS.md уже запрещает ретраи, ослабление claim и тихое лечение локатора. Добавить
закрытый список, чтобы правило было проверяемым на ревью: не переводить claim в
необязательный, не снимать `claim_id`/`assertion_id` с assert, не переключать
`ci evaluate` с `assurance` на `execution`, не добавлять `skip`/`xfail`,
не менять `expected` в плане под поведение кода без решения человека, не переводить
независимый оракул в UI-проверку. Тот же список — в completion gate `testence-repair`.

Приёмка: список в AGENTS.md и CONTRIBUTING; на него ссылается PR-шаблон (S04).

### S04. Чеклист ревью

В `PULL_REQUEST_TEMPLATE.md` раздел «Proof» состоит из команд; их проверяет CI.
Добавить раздел для человека из трёх пунктов, которые машина не проверит: сценарии
соответствуют намерению, а не текущему поведению; ожидаемые значения взяты из плана,
а не из наблюдения; ни один claim или оракул не ослаблен. Пометка: отмечает человек,
агент только отчитывается.

## 5. Фаза 2. Негативное доказательство как артефакт

### S05. ADR-0033

Определение: негативное доказательство для claim `C` теста `T` — прогон `T` с активным
объявленным негативным контролем, в котором `T` упал, и первая причина падения —
assertion с `claim_id = C`. Не считается: падение по ошибке браузера или
`inconclusive`; падение другого claim (это «wrong reason», отдельный исход);
контроль не объявлен (исход «no control», отличимый от «wrong reason»).
Отдельно зафиксировать: мок-ответы отвергаются как доказательство корректности
продукта, но для негативного доказательства они допустимы, потому что оно доказывает
способность теста падать, а не состояние продукта. ADR описывает исходы, место в
ledger, связь с verdict и почему уровень опциональный.

### S06. Объявление и включение контроля

Контроль объявляется в проекте (`testence.json`, секция `controls`: имя, описание,
что ломает) и ссылается из сценария PlanSpec (`negative_control`). Включается
`testence run --control <name>`; тест получает активное имя через фикстуру и
применяет инъекцию (`rewrite_response`, seed с дефектом). Запуск с контролем пишет
событие `control.active` в ledger; без `--control` поведение не меняется.

### S07. Ledger, `inspect`, отчёт

В `test.end` или отдельным событием: активный контроль, целевые claim, упавшие claim,
исход. `inspect` показывает по каждому claim: зелёный прогон, негативное
доказательство (run id, исход). HTML-отчёт выводит то же в таблице claim.

### S08. `ci evaluate --quality proven`

Третий режим над `assurance`: каждый обязательный claim имеет `verified` в зелёном
прогоне и негативное доказательство с исходом «right reason» в указанном
негативном прогоне (`--negative-run <dir>`). В receipt — блок
`quality.negative_proof` с перечнем claim по исходам. `ci.md` описывает режим как
опциональный и честно называет цену: второй прогон.

### S09. Регрессия

Тест в `tests/`: тест с привязанным assert, который не может упасть, проходит
`assurance`, но получает «wrong reason»/«no control» в `proven`. В `bench/corpus`
убедиться, что существующие дефекты пригодны как контроли, не дублируя корпус.

Приёмка фазы 2: `uv run pytest -q`, `uv run pytest examples -q --testence-headless`,
`testence demo run --json` без изменений результата, ADR в индексе `adr/README.md`,
схема receipt версионирована.

## 7. Что не берём и почему

| Из демо | Почему нет |
|---|---|
| OpenSpec и `openspec validate` | дублирует PlanSpec v2 и `plan validate` |
| PIT / mutation score | мутация кода приложения не применима к браузерным тестам |
| `req_coverage.py` | слабее `unverified` + `assurance`: считает наличие тега, не доказательство |
| `benchmark.sh` на патчах | `bench/corpus` уже считает right reason; у пользователей альфы нет архива дефектов |
| Defect escape rate из CSV | ручные демо-данные; в жизни источник — трекер инцидентов, вне продукта |
| Теги `step-NN` | у нас demo-spec и demo-video-script |

## 8. Риски

- Скорость: `proven` удваивает прогон. Поэтому режим опциональный, и TTTP в
  бенчмарке меряется без него.
- Не для каждого claim есть честный контроль (например, права доступа). Исход
  «no control» должен быть видим и не считаться провалом `assurance`.
- Соблазн подделать: контроль, который ломает всё подряд, даст «right reason» для
  любого claim. ADR требует, чтобы контроль был объявлен с описанием и чтобы
  упавший claim был первым, а не одним из многих.
