# Этап 6. Короткий цикл агента, хвост аудита и выпуск 0.1.0a3

Версия плана: **1.0, 2 ноября 2026**.
Исходная точка: `main` на `be7994a` (этап 5 без #58).
Статус: **в работе**: план влит (#59), T01 в PR #62.
Связь: продолжает [этап 5](../05-proof-strength/README.md); закрывает пункты 2–6 бэклога
[передачи 13 октября](../../audits/2026-10-13-handoff.md); заканчивается выпуском.

## 1. Откуда взялся план

**Пользователи не получили сделанное.** На PyPI по-прежнему `0.1.0a2` от 12 октября. С тех
пор в `main` влито около двадцати пяти PR:

- доказательство сохранения привязано к созданной записи;
- закрыты утечки в evidence; изменение несовместимое, `--attachments raw`;
- вложенный pytest владеет своими процессами;
- в паке есть история выполнения;
- вызовы API-клиента пишутся как evidence;
- добавлены негативное доказательство и `testence ci summary`.

**Бэклог передачи сверен с `main` 2 ноября.**

- Пункт 1 (зависания вложенного pytest) закрыт в #35.
- Предупреждение с секретом из id параметра исправлено
  ([аудит](../../audits/2026-10-13-sensitive-parameter-warning.md)). Сам id хранится
  по-прежнему.
- Остальное открыто:
  - `PlaywrightCdpEngine.stop()` закрывает context, browser и driver без срока
    (`engine/playwright_cdp.py`, `stop`).
  - MCP `testence_click` и `testence_fill` вызывают движок напрямую (`mcp.py`, `_click`,
    `_fill`). Подсказки о совпадениях, которую дают шаги `ex.*`, у них нет.
  - Аргументы инструментов MCP проверяются выборочно, лишние ключи не отвергаются.
  - `redaction_values` берёт только явный список `evidence.redact.env` (`config.py`).
    Переменная `API_TOKEN`, не внесённая в этот список, маскироваться не будет.
  - `LoginFailed` не несёт ни текста ошибки со страницы, ни ARIA формы.
  - Фильтра кадров трассировки нет: в аудите строка теста шла 93-й из 193.

**Строгий режим этапа 5 неудобен.** Сейчас для `proven` нужно N+1 ручных команд:

1. зелёный прогон;
2. по одному прогону на каждый контроль;
3. `ci evaluate` со всеми `--negative-run`.

Шаблон CI расписывает это вручную. Команда, которой лень, просто не включит режим.

## 2. Решения

1. **Сначала цена цикла и доверие к evidence, потом новые возможности.** Продукт
   agent-first. Лишняя сотня строк трассировки, потерянная подсказка или минута тишины
   стоят агенту токенов и ведут к неверному ремонту теста.
2. Ни один пункт не ослабляет гейты и не добавляет ретраи (AGENTS.md, CONTRIBUTING);
   это правило этапа 5 остаётся в силе.
3. **Маскирование по умолчанию закрыто.** Автоматическое правило может только добавить
   маскируемые значения, но никогда не убирает объявленные. Отключается явно, и это
   описано в `upgrading.md`.
4. **Выпуск 0.1.0a3 идёт последним** и по схеме 0.1.0a2. Решение go и запуск
   `publish.yml` даёт владелец. Выпуск несовместим из-за #32, и заметки к выпуску
   говорят это первой строкой.
5. **P1-7 и прогоны с моделью в план не входят.** Нужны хост агента, модель и внешние
   люди, из автономной сессии это честно не сделать (раздел 8).

## 4. Фаза 1. Короткий цикл агента

### T01. Трассировка падения начинается с теста

Сначала замер на упавшем примере: на какой строке трассировки стоит строка теста и
сколько строк всего. Это делается до правки, и цифры идут в PR.

**Что сделать.**

- Кадры Testence (`dsl`, `engine`, `evidence`) и Playwright скрываются через
  `__tracebackhide__` или фильтр `excinfo.traceback` в `pytest_runtest_makereport`.
- Свои хелперы пользователя не скрываются.
- Выключатель для отладки самого фреймворка: `--testence-full-trace` и
  `TESTENCE_FULL_TRACE=1`.
- В выводе остаётся строка «скрыто кадров: N, полная трасса: `--testence-full-trace`».

**Приёмка.**

- Регрессионный тест: строка теста среди первых пяти кадров, кадров Testence нет.
- С выключателем кадры Testence на месте.
- `error_trace` в ledger и паке получает то же сокращение.
- Замороженные файлы тестов не меняются.

### T02. MCP отвечает как шаги `ex.*`

- **Ошибки `testence_click` и `testence_fill`** несут ту же подсказку, что шаг `ex.click`:
  сколько элементов совпало и кандидаты с их `Target`. Источник один: общая функция
  диагностики шага, без копии.
- **Аргументы проверяются по `inputSchema` каждого инструмента.** Неверный тип и
  лишний ключ дают `ToolError` с именем ключа.
- **`testence_doctor` с `ok: false`** возвращает `isError: true`.
- **Тесты** гоняют MCP-сервер в процессе на каждом пути: ошибка взаимодействия, неверный
  тип, лишний ключ, провал doctor.

### T03. Документы агента обещают только установленное

- **`agent-workflow.md`.** Список файлов в нём сверяется с тем, что реально пишет
  `agent install`. Тест сравнивает документ с выводом установщика для каждого клиента,
  чтобы расхождение не вернулось.
- **Навык `testence-plan`** говорит, что план с `oracles: api` требует блока `readiness`,
  иначе `plan prepare` его блокирует. Пример блока прилагается.
- Версия skill pack поднимается.

### T04. Первый час

- **`LoginFailed`** несёт текст ошибки со страницы (`role=alert`, `aria-invalid`,
  видимое сообщение у формы) и ARIA формы. Оба значения проходят маскирование проекта.
- **`doctor`** печатает строку перед каждой долгой пробой («запуск браузера…»), чтобы до
  90 секунд тишины больше не было. В `--json` эти строки не попадают.
- **`TRIAGE.md`** начинается с того, что увидеть человеку. Обращение к агенту уходит
  ниже.

## 5. Фаза 2. Строгий режим одной командой

### T05. `testence prove`

`testence prove [PATHS] [--control NAME ...] [--run-id ID]`.

**Что делает команда.**

- Выполняет зелёный прогон, затем прогон на каждый объявленный контроль, или только на
  перечисленные.
- Оценивает их как `ci evaluate --quality-mode proven` и пишет один receipt.
- Код выхода тот же, что у `ci evaluate`.
- Каталоги прогонов: `runs/<ID>` и `runs/<ID>-<control>`.
- Красный зелёный прогон останавливает команду: негативные прогоны не выполняются.

**Решения внутри пункта.**

- **Сужение негативного прогона до тестов с целевыми claim.** Делается, только если claim
  известны до запуска, то есть на этапе сбора. Если нет, гоняется весь выбор, а сужение
  записывается в открытые вопросы.
- **Доля побочных падений по контролю** (сработка ADR-0033: больше половины) выводится
  предупреждением в `prove`, `ci summary` и receipt. Гейт она не меняет.

**Документы и приёмка.**

- Шаблон в `docs/examples/github-actions.yml` и `ci.md` сворачивается до одного шага.
  Ручной путь остаётся описанным.
- Приёмка: реальный прогон демо-проекта. `testence prove` даёт `proven` на
  `onboarding.proof.recorded` и код 0. Для сравнения пустышка из регрессии этапа 5 даёт
  код 1.

## 6. Фаза 3. Хвост безопасности evidence

### T06. Автомаскирование секретных переменных окружения

**Правило.**

- Значения переменных, имена которых подходят под шаблон, добавляются к
  `redaction_values`.
- Шаблон без учёта регистра: `*TOKEN*`, `*SECRET*`, `*PASSWORD*`, `*PASSWD*`,
  `*API_KEY*`, `*PRIVATE_KEY*`, `*CREDENTIAL*`.
- Не маскируются значения короче 8 символов, а также похожие на булево значение или
  число.
- Отключение: `evidence.redact.auto_env: false`.

**Видимость.**

- `doctor` перечисляет имена переменных, попавших под шаблон. Значения не выводятся.
- `upgrading.md` описывает новое поведение.

**Приёмка.** Канарейка в переменной `SYNTH_API_TOKEN` не встречается ни в одном
артефакте: ledger, пак, экспорт, отчёт, ответ MCP.

### T07. Секреты вне значений

Открыто три пути.

- **Id параметров** (`test_x[SECRET]`) попадают в nodeid, manifest и экспорт.
  Внутри id маскируются только известные секреты, по `redaction_values`. Identity и
  digest считаются по исходному значению локально. Экспорт показывает маскированное.
  Тест подтверждает, что история Allure не расходится между двумя прогонами.
- **Строки исходника** в `error_trace` проходят маскирование.
- **`fingerprints.json`** вместо текста нажатого элемента хранит маскированный текст.

На каждый путь — тест с канарейкой, который падает на `main`.

### T08. Структурное маскирование CSV, XML, HTML

Вложения этих типов маскируются по структуре.

- В HTML: значения `value`, полей `password` и `hidden`.
- В XML: текст и атрибуты.
- В CSV: ячейки столбцов с секретными заголовками.

Обычная текстовая замена остаётся вторым проходом. Тест: канарейка в каждом формате и
нетронутая структура файла.

## 7. Фаза 4. Надёжность

### T09. Закрытие движка со сроком

**Что сделать.**

- `stop()` получает срок на каждый шаг: закрытие context, закрытие browser, остановка
  driver.
- Если шаг завис, сторожевой таймер убивает дерево процессов своего браузера и драйвера
  по PID, известному с запуска. Это переиспользует `_process`, на Windows через Job.
  Синхронный вызов Playwright после этого возвращается сам; переносить sync API в другой
  поток нельзя.
- В evidence пишется событие с превышенным шагом.

**Граница.** Подключённый по CDP чужой браузер не убивается никогда.

**Тест.** Фейковый зависающий драйвер: `stop()` возвращается в пределах срока, процессы
мертвы.

### T10. Две нестабильные задачи CI

- «unexpected outcome» в Visual client simulation;
- бюджет по реальному времени в `bench/scale_profile --check`.

**Порядок работы.**

1. Собрать логи падений из истории CI и записать причину.
2. Исправить причину.
3. Ретраев не добавлять. Бюджет `scale_profile` перевести на измерение, которое не
   зависит от загрузки раннера: процессорное время или отношение к контрольному замеру.

## 10. Риски

- **T01 спрячет ошибку фреймворка.** Строка о скрытых кадрах и выключатель видны в каждом
  падении. Регрессия проверяет, что выключатель работает.
- **T06 замаскирует короткие или общие значения и испортит evidence.** Против этого —
  минимальная длина, пропуск булевых и чисел, перечень имён в `doctor` и явное
  отключение.
- **T07 разведёт историю в Allure и TestOps.** Identity считается по исходному значению.
  Маскирование касается только показа, тест сверяет историю двух прогонов.
- **T09 убьёт чужой процесс.** Убиваются только PID, запущенные этим движком.
  Подключённый браузер исключён тестом.
- **T05 удвоит время CI у тех, кто включит `prove`.** Это цена `proven` (сработка
  ADR-0033 по времени). Режим остаётся опциональным.
- **T11 необратим.** Выполняется только по слову владельца.
