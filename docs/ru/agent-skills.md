# Переносимые Agent Skills

Testence поставляет один версионированный набор skills внутри Python-дистрибутива. Это слой рабочего процесса между намерением пользователя и детерминированными контрактами Testence; в нём нет SDK конкретной модели, учётных данных провайдера или клиентской бизнес-логики.

Текущий набор: `testence/skill-pack/1`, версия `0.1.7`.

## Четыре фазы

| Skill | Когда вызывать | Проверяемое условие завершения |
|---|---|---|
| `testence-plan` | для функции, риска, issue или изменения нужно определить покрытие | валидный `testence/planspec/2` с проверенными claims и oracles |
| `testence-author` | утверждённый план нужно превратить в исполняемое покрытие | детерминированный pytest-код, доказанный по схеме green → ожидаемый red → green, с привязкой claims |
| `testence-triage` | привязанный тест упал и создал evidence pack | полный по claims и привязанный к pack `testence/verdict/2` либо явное воздержание |
| `testence-repair` | валидный verdict допускает обслуживание теста | видимый минимальный diff и целевой proof без ослабления claims |

Фазы разделены, потому что у них разные полномочия. Планирование не должно менять код, triage — незаметно его чинить, а repair обязан отказаться переписывать тест вокруг `real_bug`.

## Единый источник

Канонические файлы лежат в `src/testence/agent/skills/`; `skill-pack.json` фиксирует версию набора, версии публичных контрактов, входы/выходы фаз и политику безопасного обновления. Они входят в package data, поэтому установленный wheel содержит ровно те же артефакты, что и исходный репозиторий.

Пути клиентов — это адаптеры установки, а не форки:

| Клиент | Адаптер проекта |
|---|---|
| Codex | копировать/связывать четыре каталога в `.agents/skills/` |
| OpenCode | использовать ту же установку `.agents/skills/` |
| Claude Code | копировать/связывать те же каталоги в `.claude/skills/` |
| ChatGPT или управляемая поставка | включать те же каталоги как skills плагина |
| другие клиенты | использовать каталог Agent Skills, если он поддерживается, иначе давать ссылки на публичный workflow и CLI |

`agents/openai.yaml` добавляет необязательные UI-метаданные Codex. Другие клиенты его игнорируют; поведение остаётся в стандартном `SKILL.md` и references.

## Установка и проверка

Установите точный встроенный pack в один или оба проектных адаптера:

```bash
testence agent install --project . --client codex --client claude --json
testence agent verify --project . --client codex --client claude --json
```

Codex получает `.agents/skills/<skill>/`, Claude Code —
`.claude/skills/<skill>/`. Оба дерева копируются из установленного дистрибутива
Testence. Команда фиксирует digest pack и каждого принятого файла в
`.testence/agents.json`. Exit `0` означает installed/valid, `2` — некорректный ввод
или state, `3` — локальный конфликт или drift.

Реализованный контракт обновления:

1. читать manifest из установленного пакета, а не загружать изменяемые промпты во время работы;
2. принимать только явно выбранные поддерживаемые клиенты и перечислять пути в receipt;
3. устанавливать идентичное содержимое через тонкие адаптеры;
4. записывать версию набора, адаптер, пути и SHA-256 каждого установленного файла в `.testence/agents.json`;
5. при обновлении заменять файл, только если его текущий hash совпадает с hash предыдущей установки;
6. сохранять локально изменённый файл и повторяемо показывать конфликт для ручного merge;
7. атомарно писать state и перечислять установленные, неизменённые и конфликтные файлы;
8. никогда не помещать credentials, target URL, пользовательские данные или evidence внутрь skill.

Версии набора следуют SemVer. Любое изменение инструкции или reference увеличивает версию набора. PlanSpec, evidence и verdict имеют собственные версии; ломающий контракт требует новой версии контракта и совместимого релиза skill-pack.

## Release gate

Каждый релиз skills проверяется на:

- прямом вызове по имени;
- косвенном естественном запросе, соответствующем description;
- неполном вводе, который должен привести к полезному gate или воздержанию;
- близком запросе, который не должен активировать skill;
- golden path plan → author → triage → repair;
- проверке наличия manifest и всех файлов в wheel;
- smoke-тестах обнаружения и загрузки references в каждом клиенте.

Метрики: успех задачи, валидность контрактного выхода, нарушения policy, лишние tool calls, время и токены. Улучшение промпта принимается, только если эти показатели растут без ослабления safety gates.

## Текущая граница

Переносимый pack, безопасный при конфликтах installer, проверка целостности,
метаданные, manifest и проверки wheel реализованы.
