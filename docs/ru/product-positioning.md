# Позиционирование продукта

## Категория

**Agent-native UI verification — агентно-ориентированная верификация UI.**

Testence — это слой верификации между coding agent и веб-приложением. Агент планирует,
создаёт и поддерживает тесты; Testence детерминированно воспроизводит их и возвращает
структурированные доказательства, на основании которых агент выносит вердикт.

Это намеренно более узкая и защищаемая категория, чем «AI-платформа для тестирования»:

- **agent-native**, потому что основной оператор — Claude Code, Codex/ChatGPT,
  OpenCode или другой coding agent с доступом к инструментам;
- **UI verification**, потому что реальные пользовательские пути в браузере —
  основная поверхность продукта;
- **verification layer**, потому что Testence предоставляет контракты исполнения,
  доказательств и политик, а не ещё одного автономного агента общего назначения.

«Agent-first» определяет, **кто управляет продуктом и рабочим процессом**. «AI-first»
определяет, **где применяется интеллектуальное суждение**. Во внешней коммуникации
следует начинать с *agent-native*: понятие «AI-first testing» слишком широко и легко
ассоциируется с шагами на естественном языке или LLM внутри каждого запуска — ни то,
ни другое не является базовой моделью Testence.

## Обещание продукта

> Дайте своему coding agent описание функции. Получите проверяемый план тестирования,
> детерминированные UI-тесты и вердикты, подкреплённые доказательствами.

Короткая версия:

> **Планируйте с AI. Воспроизводите детерминированно. Судите по доказательствам.**

Входом может быть запрос на функцию, баг-репорт, pull request или описание продуктового
риска. Долговечный результат — не диалог с агентом, а набор артефактов репозитория и
запуска: план, исполняемый тестовый код, журнал доказательств, вердикт и, когда это
уместно, проверяемое предложение изменения.

## Для кого предназначен продукт

| Роль | Ответственность |
|---|---|
| coding agent | основной оператор: планирует покрытие, исследует UI, пишет и запускает тесты, интерпретирует доказательства и предлагает изменения |
| разработчик или владелец QA | задаёт намерение, риск и политику; проверяет планы, чувствительные операции и изменения исходников |
| CI | воспроизводит принятые тесты без LLM и сохраняет переносимые артефакты |
| Testence | обеспечивает общие для всех детерминированное исполнение, доказательства, схемы и правила согласования |

Agent-first не означает отсутствие человека. Люди владеют намерением и политикой,
агенты выполняют частую операционную работу, а детерминированное ПО фиксирует, что
действительно было выполнено и записано.

## Проблема

Coding agents уже умеют создавать прикладной код, но верификация UI всё ещё разрывает
их цикл в трёх местах:

1. Браузерные агенты могут исследовать UI, но повторные действия под управлением модели
   медленны, дороги и плохо воспроизводятся в CI.
2. Традиционные test runners быстры, но их правила написания тестов и артефакты падений
   спроектированы прежде всего для людей.
3. AI-native продукты для тестирования часто скрывают исполнение, healing или выбор
   модели за hosted-платформой, уменьшая контроль и проверяемость.

Testence делает исследование одноразовым, а верификацию — долговечной. AI применяется
там, где ценно суждение; принятое поведение компилируется в обычный детерминированный
код.

## Модель продукта

В Testence явно выделены три контура.

### 1. Контур управления агентом

- инструкции проекта сообщают, когда следует применять Testence;
- версионированные skills обучают процессам планирования, написания, триажа и
  сопровождения;
- небольшая поверхность CLI/MCP предоставляет высокоуровневые типизированные операции;
- адаптеры делают один и тот же контракт доступным в разных агентских клиентах.

Этот контур может использовать LLM. Он нейтрален к провайдеру и заменяем.

### 2. Контур детерминированной верификации

- pytest-тесты и UI DSL, сохраняющий намерение;
- браузерное исполнение на Playwright и API-oracles в той же сессии;
- версионированный журнал событий, ограниченные evidence packs и экспортёры отчётов;
- воспроизводимое локальное и CI-исполнение без вызова модели в стандартном пути.

Этот контур — доверенный источник истины об исполнении.

### 3. Контур доверия и управления

- схемы и provenance связывают намерение, план, сгенерированный код, запуск и вердикт;
- политики редактирования и хранения защищают собранные данные приложения;
- permission gates разделяют наблюдение, исполнение и изменение исходников;
- healing является предложением с доказательствами и целевым повторным запуском, а не
  скрытой мутацией.

Этот контур делает автономность агента проверяемой, а не непрозрачной.

## Принципы продукта

1. **Агент — основной UX.** Пользователь должен иметь возможность описать функцию или
   риск, не изучая сначала внутренности фреймворка.
2. **Каждая фаза оставляет проверяемый артефакт.** Важное состояние не должно
   существовать только в контексте чата или памяти модели.
3. **При воспроизведении LLM не обязателен.** Принятые тесты выполняются локально и в
   CI как детерминированный код.
4. **Никакого скрытого self-healing.** Изменение селектора или проверки — это
   предложенный diff исходников с причиной, уверенностью и доказательствами.
5. **Нейтральность к провайдеру закреплена контрактом.** Интеграции используют
   переносимые skills, инструкции репозитория, CLI и MCP, но не SDK модели в runner.
6. **UI-first, API-supported.** API подготавливает состояние и даёт независимые
   oracles; предметом тестирования остаётся браузерный путь.
7. **Неопределённость — это данные.** Агент может воздержаться, указав доказательства
   в `blocked_on`; он не должен выдумывать уверенность.
8. **Политика принадлежит владельцу.** Люди определяют, что можно выполнять или менять
   автоматически, вместо ручного одобрения каждого клика.

## Задачи пользователя

- «Агент, покрой эту функцию долговечными UI-тестами».
- «Агент, докажи, что этот pull request не сломал критические пользовательские пути».
- «Агент, объясни причину красного запуска и покажи доказательства».
- «Агент, безопасно обнови тесты после намеренного изменения UI».

Это публичные рабочие процессы продукта. Конкретные локаторы, скриншоты и pytest-хуки —
детали их реализации.

## Чем Testence не является

- агентом общего назначения для управления браузером;
- recorder или low-code редактором тестов;
- API-first платформой тестирования;
- собственным облаком браузеров и устройств;
- hosted dashboard, владеющим тестами пользователя;
- runtime-движком действий на естественном языке в обычном CI;
- автономным healer, которому разрешено переписывать тесты без проверки.

## Конкурентный клин

Playwright Test Agents делают связку «runner плюс workflow coding agent» базовым уровнем.
Поэтому Testence должен выигрывать качеством контракта верификации, а не одной лишь
генерацией тестов:

- переносимые, ограниченные доказательства, спроектированные как вход агента;
- трассируемость от продуктового утверждения до вердикта;
- независимая проверка согласованности UI и API;
- явные границы разрешений и review;
- измеримые доли false green, false red и падений по неверной причине;
- local-first тесты и нейтральные к провайдеру интеграции.

Защитный ров — **доверенное замыкание агентного цикла разработки**: агент проходит от
запроса до доказательства, не превращая верификацию в непрозрачную сессию модели.

## Иерархия сообщений

**Категория на главной странице:** Agent-native UI verification.

**Заголовок:** UI verification, созданная для coding agents.

**Подзаголовок:** Дайте Claude, ChatGPT/Codex, OpenCode или другому coding agent
описание функции. Testence превратит его в проверяемый план, детерминированные
браузерные тесты и вердикты с доказательствами — без вызовов модели в обычном CI.

**Подтверждения обещания:**

- детерминированное воспроизведение со скоростью test runner;
- структурированные доказательства вместо свалки скриншотов;
- UI-действия, проверенные по независимому состоянию API;
- проверяемые предложения исправлений вместо скрытого healing;
- открытые артефакты и отсутствие обязательного model provider.

## Критерий успеха

Продукт становится agent-native, когда новый пользователь может передать
поддерживаемому coding agent запрос на функцию и, не изучая вручную внутренности
Testence, получить:

1. понятный план, который можно согласовать;
2. принадлежащий пользователю детерминированный тест;
3. воспроизводимый запуск с полной цепочкой доказательств;
4. типизированный вердикт при падении;
5. проверяемый patch, когда требуется сопровождение.
