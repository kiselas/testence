# Синтетическая таксономия отказов

Testence оценивает себя через seeded behaviours с заранее известными исходами.
Таксономия нейтральна к продукту и намеренно достаточно мала для аудита.

## Классы исходов

| Класс | Ожидаемый исход runner | Ожидаемый triage verdict |
|---|---|---|
| поведенческий дефект | red | `real_bug` |
| ошибка реализации теста при согласованных продукте и PlanSpec | red | `test_bug` |
| drift адреса | red плюс проверяемое предложение | `ui_change` |
| нестабильность времени | red с timing evidence | `flaky_timing` |
| безвредный control | green | `none` |
| несовпадение окружения | red | `environment` |
| согласованное изменение поведения | red | `behaviour_change` либо provisional с `blocked_on` |

## Уровни обманчивости

Динамический корпус коллекции дополнительно помечает дефекты по требуемому наблюдению:

- **N — naive:** достаточно широкой проверки видимого состояния.
- **P — precise:** дефект ловит только точный assertion.
- **O — oracle:** UI выглядит правдоподобно, нужен независимый API oracle.
- **A — intermittent:** один запуск, скорее всего, пройдёт; нужны повторные или
  параллельные наблюдения.

Controls не получают уровень: их задача — измерять false-red behavior.

## Реализованные семейства

Текущий синтетический target покрывает:

- молча отброшенное первое interaction;
- view, не догоняющее состояние после успешной записи;
- постоянные placeholders;
- удалённые rows, остающиеся в списке;
- проигнорированное состояние deep link;
- counters и page windows, расходящиеся с API;
- поиск только по prefix, когда обещан substring;
- потерянный filter;
- drift accessible name с heal proposal;
- безвредные restyling, reordering и wrapping;
- медленные responses, несущественный console noise и явный Enter-to-commit design.

Старый static-page корпус покрывает переименование локатора, удаление элемента, неверные
значения, бездействующие actions, delayed async results и безвредную перестройку DOM.

## Правила

1. Каждый item называет утверждение, которое должно упасть. Другое падение является
   collateral, а не успешным обнаружением.
2. Нужны и defects, и controls. Фреймворк, ловящий всё за счёт падения всего, бесполезен.
3. Interaction retries отключены, потому что некоторые дефекты скрываются повтором.
4. Heal proposal никогда не меняет выполняемый тест; это evidence для review.
5. Публикуемые scores обязаны указывать revision корпуса, repeats, browser и hardware.
6. `test_bug` требует положительного доказательства claim из PlanSpec; одного факта,
   что изменение assertion сделает тест зелёным, недостаточно.

Source-of-truth определения находятся в `corpus/items.py` и
`bench/corpus/items.py`. Документ описывает стабильные категории, но не заявляет
покрытие ещё не реализованных сценариев.
