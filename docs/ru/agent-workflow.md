# Рабочий процесс агента

Этот документ определяет публичный workflow Testence. PlanSpec, привязка claim'ов к
pytest, их перенос в ledger/evidence pack, валидация verdict и переносимый skill-pack
уже работают. CLI bootstrap, безопасная установка skills и сохранение verdict тоже
реализованы. Визуальное исследование выполняет агент по packaged reference;
управляемый discovery service и MCP остаются будущей работой.

## Прозрачный конвейер

```text
намерение человека / PR / риск
          │
          ▼
   PlanSpec (проверяемые утверждения и сценарии)
          │
          ▼
   управляемое исследование UI ──► детерминированный Python-тест + ActionMap
          │                                  │
          └──────── журнал исследования      ▼
                                      runner Testence (без LLM)
                                              │
                                              ▼
                                  run.jsonl + evidence pack
                                              │
                                              ▼
                                   типизированный вердикт агента
                                              │
                            ┌─────────────────┴────────────────┐
                            ▼                                  ▼
                    продуктовый дефект               предложение сопровождения
                                                               │
                                                               ▼
                                                    review + целевой перезапуск
```

Правило простое: каждая стрелка пересекает файл или версионированный протокол.
Пользователь может остановиться после любой фазы, проверить результат и продолжить
работу с другим совместимым агентом.

## Участники и полномочия

Человек определяет задачу, приемлемый риск и политику разрешений. Coding agent
координирует workflow. Testence отвечает за детерминированное исполнение и целостность
доказательств. CI воспроизводит уже принятые тесты.

Агент может работать автономно внутри согласованной границы, но он никогда не является
источником истины о том, выполнился ли браузерный шаг или прошёл oracle. Источник истины —
журнал.

## Полный жизненный цикл

| Фаза | Действие агента | Долговечный артефакт | Gate по умолчанию |
|---|---|---|---|
| 0. Bootstrap | обнаруживает проект, проверяет окружение и загружает workflow Testence | конфигурация проекта, инструкции агента, результат doctor | пользователь согласует установку и запись конфигурации |
| 1. Plan | превращает функцию или риск в явные утверждения, сценарии, данные и oracles | PlanSpec `specs/<feature>.md` | review плана для нового покрытия |
| 2. Prepare | проверяет auth, изоляцию seed, безопасность target и политику артефактов | результат preflight и ссылки на seed | разрушительные записи и общее окружение требуют согласования |
| 3. Discover | исследует управляемый браузер, узнаёт реальный UI и проверяет действия-кандидаты | ограниченный журнал исследования и fingerprints | навигация и действия внутри согласованного target автоматичны |
| 4. Compile | пишет детерминированный pytest/DSL-код и изменения ActionMap проекта | diff исходников с ID плана и утверждений | изменения исходников остаются проверяемыми |
| 5. Prove | запускает новый тест и проверяет селекторы, assertions и независимые oracles | журнал, доказательства и отчёт генерации | тест не принимается только на основании факта генерации кода |
| 6. Replay | выполняет принятые тесты локально или в CI без LLM | `run.jsonl`, summary и отчёты | обычные разрешения на запуск тестов |
| 7. Judge | читает ограниченный отредактированный failure pack и классифицирует результат | `verdict.json` | по умолчанию read-only; неопределённость допустима |
| 8. Propose | готовит изменение локатора, assertion или теста, когда доказательства указывают на drift | объяснение, patch и область перезапуска | никогда не применяется скрыто |
| 9. Review | применяет принятое предложение и запускает минимальную доказательную область | решение review и связанный запуск | решает человек или политика репозитория |
| 10. Learn | обновляет трассируемость, fingerprints и агрегированные метрики качества | история покрытия и сопровождения | без зависимости от непрозрачной памяти модели |

## 1. Bootstrap

Переносимые workflow-артефакты можно установить для одного или обоих поддерживаемых
клиентов и затем проверить побайтово:

```bash
testence agent install --project . --client codex --client claude --json
testence agent verify --project . --json
```

Installer не копирует секреты в конфигурацию агента. Он записывает repo-owned receipt
`.testence/agents.json`, обновляет только неизменённые ранее установленные файлы и
сообщает о локальных правках как о конфликтах.

Устанавливаемый контракт включает:

- короткую инструкцию репозитория о том, когда агент должен вызывать Testence;
- переносимые Agent Skills для `plan`, `author`, `triage` и `repair`;
- необязательные клиентские адаптеры там, где отличаются правила обнаружения;
- конфигурацию проекта Testence и синтетический seed-тест;
- `testence doctor`, проверяющий Python, доступ к browser/CDP, возможность записи
  артефактов, выбор профиля и настройки чувствительных данных.

Bootstrap-отчёт должен перечислять каждый созданный или изменённый файл.

## 2. Планирование до открытия браузера

PlanSpec — понятный человеку Markdown с машиночитаемыми идентификаторами. Он фиксирует:

- функцию, пользователя и бизнес-риск;
- проверяемые утверждения и их приоритет;
- предусловия и детерминированные seed-данные;
- позитивные, негативные и permission-сценарии;
- ожидаемое наблюдение в UI;
- независимый oracle, когда он доступен;
- исключения, неопределённость и требуемые согласования.

В v2 машиночитаемый контракт стабилизирует `project_id`, metadata plan, claims с типами
oracle и scenarios, чьи ID являются логическими case ID. Preconditions, seed/cleanup и approvals пока
остаются в окружающем Markdown; расширять schema будем после проверки authoring corpus,
а не заранее.

Markdown-файл содержит ровно один JSON-блок `testence-planspec`; остальной текст
остаётся свободным контекстом для человека и агента:

```testence-planspec
{
  "schema": "testence/planspec/2",
  "project_id": "checkout",
  "id": "checkout.discount",
  "title": "Apply an eligible discount",
  "claims": [
    {
      "id": "checkout.discount.total",
      "statement": "The UI and cart API expose the same discounted total.",
      "oracles": ["ui", "api"],
      "required": true
    }
  ],
  "assertions": [
    {
      "id": "assert.discount.total",
      "claim_id": "checkout.discount.total",
      "oracle": "api",
      "required": true,
      "expected": "Cart API и UI показывают одинаковую итоговую сумму."
    }
  ],
  "scenarios": [
    {
      "id": "eligible-code",
      "title": "Apply an eligible code",
      "claims": ["checkout.discount.total"],
      "risk": "false green from an optimistic UI"
    }
  ]
}
```

План проверяется до запуска, а тест привязывается только к объявленным claim ID:

```bash
testence plan validate specs/checkout-discount.md --json
```

```python
@pytest.mark.testence(
    plan="specs/checkout-discount.md",
    case_id="eligible-code",
    claims=["checkout.discount.total"],
)
def test_discount_total(ex):
    ...
```

PlanSpec — семантический якорь. Pytest отклоняет неверный путь или неизвестный claim на
collection, а Testence добавляет `plan` и `claims` ко всем событиям связанного теста,
failure pack и HTML-отчёту.

## 3. Сначала исследование, затем компиляция

Исследование UI происходит во время authoring. Агент может использовать браузер или
другой discovery backend, чтобы изучить приложение и проверить селекторы, действия и
assertions. Затем результат компилируется в обычный Python и DSL Testence, сохраняющий
намерение.

Решения исследования должны быть проверяемыми: кандидаты целей, выбранная доступная
идентичность, отклонённые неоднозначности и существенные fingerprints. Сырые действия
под управлением модели не являются артефактом, продвигаемым в CI.

## 4. Доказательство сгенерированных тестов

Для UI-oracle привязывайте проверку состояния:
`ex.expect_visible(..., assertion_id="...", claim_id="...")`.
Проверяйте `testence inspect <run-dir> --json`: зелёного pytest недостаточно,
для принятого здорового сценария нужны `verified` и отсутствие integrity errors.

Сгенерированный код — только гипотеза. До предложения принять его агент обязан:

1. выполнить точный сгенерированный код на объявленном target;
2. подтвердить, что у каждого утверждения плана есть assertion или oracle;
3. подтвердить изолированность и повторяемость seed-данных;
4. воспроизвести ожидаемое падение, если доступен seeded defect или negative control;
5. повторно получить зелёный результат на чистом seed;
6. сообщить о непокрытых утверждениях и неразрешённой неоднозначности.

Так правдоподобно выглядящий тест не будет принят за проверенное покрытие.

## 5. Воспроизведение без агента

После принятия тест выполняется текущим Testence/pytest runner. Обычный CI не зависит от
модели. Его стабильные результаты — версионированный журнал и производные
представления; агент вызывается позже, только когда требуется суждение.

Такое разделение делает стоимость предсказуемой, а результат — воспроизводимым.

## 6. Вердикт по доказательствам

При падении агент получает минимальный отредактированный pack, достаточный для решения,
и заполняет находящийся в нём `verdict.template.json`. Контракт вердикта:

```json
{
  "schema": "testence/verdict/2",
  "project_id": "checkout",
  "case_id": "discount-total",
  "variant_id": "default",
  "attempt_id": "attempt-controller-1",
  "run_id": "r-20260906-120000-abc123",
  "proof_id": "proof-0123456789abcdef0123",
  "plan_digest": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "test_digest": "sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "policy_digest": "sha256:cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc",
  "pack_digest": "sha256:dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd",
  "plan_id": "checkout.discount",
  "test_id": "tests/test_checkout.py::test_discount_total",
  "verdict": "real_bug",
  "confidence": 0.91,
  "summary": "UI показал скидку, но cart API вернул прежнюю сумму.",
  "claim_results": [
    {
      "claim_id": "checkout.discount.total",
      "status": "failed",
      "reason": "UI и authoritative API расходятся.",
      "evidence": ["oracle.json#/0", "network.jsonl"]
    }
  ],
  "blocked_on": []
}
```

Допустимые значения `verdict`: `real_bug`, `test_bug`, `behaviour_change`,
`ui_change`, `flaky_timing` и `environment`. `test_bug` означает, что продукт и
актуальный PlanSpec согласованы, а реализация теста противоречит им. `blocked_on` —
явный канал воздержания: он
называет недостающее доказательство вместо изобретения шестого класса причин. Вердикт
с `null` требует хотя бы один blocker; `passed`/`failed` claim требует ссылки на реально
существующие файлы pack. Проверка связывает verdict с точными plan, test и claims,
проверяет digests plan/test/policy/pack, каждый artifact manifest и каждый JSON Pointer
на принадлежность той же попытке:

```bash
testence verdict validate runs/<run>/<test>/pack/verdict.json \
  --plan specs/checkout-discount.md --json
```

## 7. Предлагать, но никогда не исправлять скрыто

Когда доказательства указывают на `ui_change` или принятое `behaviour_change`, агент
может создать предложение сопровождения. Оно включает:

- затронутые утверждение и шаг;
- старую и предлагаемую цель или assertion;
- доказательства fingerprint и кандидатов;
- объяснение причины и уверенность;
- точный diff исходников;
- минимальный перезапуск, способный подтвердить изменение.

Source proposal использует `testence/repair-proposal/1` и связывает файл verdict,
защищённую семантику PlanSpec и исходное состояние source через SHA-256. Он действителен
только с одним verified healthy run, одним violated defect control и одним verified
harmless control:

```bash
testence repair validate repair.json --verdict <pack>/verdict.json \
  --plan specs/checkout-discount.md --base tests/test_checkout.py \
  --pack <pack> --evidence-root proof-runs --json
```

Применение patch — отдельное действие с разрешением. Принятие или отклонение хранится
как обратная связь о качестве, но никогда как скрытое runtime-поведение.

## Контракт интеграции

Переносимое ядро должно следовать открытому соглашению Agent Skills и оставаться
доступным через CLI. Клиентская упаковка намеренно тонкая:

| Клиент | Поверхность обнаружения и инструкций | Интеграция Testence |
|---|---|---|
| Codex / ChatGPT | проектный `AGENTS.md`, skills и необязательный plugin/MCP server | универсальные skills и типизированные инструменты Testence |
| Claude Code | `CLAUDE.md`, Agent Skills, plugins и MCP | те же skills, тонкий instruction shim и тот же MCP-контракт |
| OpenCode | `AGENTS.md`, `.agents/skills` и MCP | те же skills и MCP-контракт |
| другие агенты | Agent Skills при поддержке, иначе документация репозитория и CLI | без fork runner или формата артефактов |

Skills определяют, **когда и в каком порядке** использовать Testence. Инструменты MCP
или CLI выполняют **ограниченные действия** и возвращают структурированные данные. Они
не должны дублировать бизнес-логику runner.

Начальная поверхность MCP должна быть небольшой и ориентированной на задачи:

- `project_status` — проверить конфигурацию, возможности и состояние безопасности;
- `plan_validate` — проверить PlanSpec и ID трассируемости;
- `session_start` — создать управляемую authoring-сессию;
- `run` — выполнить объявленную область и вернуть ссылки на запуск и артефакты;
- `failure_pack_get` — вернуть ограниченный pack упавшего теста;
- `verdict_submit` — проверить и сохранить типизированный вердикт;
- `repair_propose` — подготовить проверяемое предложение и область целевого перезапуска.

Изменение исходников на первом этапе остаётся обычной правкой агента под контролем
permissions клиентского приложения. Testence не нужен привилегированный универсальный
инструмент редактирования файлов.

## Модель разрешений

| Класс действия | Рекомендуемое значение по умолчанию |
|---|---|
| чтение конфигурации проекта, планов и отредактированных доказательств | разрешить |
| проверка плана или статуса проекта | разрешить |
| исследование и запуск на явно согласованном локальном или тестовом target | разрешить для этого target |
| создание изолированных seed-данных через объявленный адаптер | разрешить, если обратимо |
| запись планов или сгенерированных тестов | создавать видимый diff |
| изменение принятого assertion или локатора | требовать предложение и доказательный перезапуск |
| работа с общими/production-данными, ослабление oracle или раскрытие неотредактированных доказательств | явное согласование или запрет |

Политика хранится в конфигурации репозитория, чтобы границы сохранялись при смене
агентского клиента.

этому контракту.

## Почему эта форма переносима

Основные экосистемы coding agents уже разделяют постоянные workflow-инструкции и
вызываемые инструменты. OpenAI описывает skills как повторяемые workflows, а MCP — как
типизированный доступ к инструментам; Claude Code предоставляет ту же комбинацию
инструкций, Agent Skills и MCP; OpenCode обнаруживает переносимые skills и инструкции
проекта. Поэтому Testence может поставить один workflow и один протокол инструментов
вместо встроенного собственного агента.

## Автономная визуальная регрессия

Опциональный `testence[visual]` добавляет `ex.expect_screenshot`: сравнение viewport
с проверенным эталоном, закреплённым по SHA-256. Требуются явное разрешение захвата
и привязка UI assertion к PlanSpec. Пропавший или подменённый эталон, нестабильный
кадр и другой профиль дают `inconclusive`; визуальное расхождение даёт нарушение.
Эталон не обновляется при повторном прогоне.

[Клиентская эмуляция](../../bench/client_simulation/README.md) устанавливает wheel
в изолированные проекты, проверяет форматы Codex/Claude и выполняет визуальные
контроли с передачей пакета скриптовому судье. Это один скриптовый исполнитель,
а не независимые запуски моделей. Подробнее: [ADR-0023](adr/0023-visual-baseline-proof.md).
