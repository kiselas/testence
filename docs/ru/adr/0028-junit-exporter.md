# ADR-0028: Экспортер JUnit рядом с `--junitxml`

Статус: accepted (уточняет ADR-0013).

## Контекст

ADR-0013 оставил JUnit XML за `pytest --junitxml`: он правильно пишет файл под `-n`, и
его разбирает любой CI. Но в этом файле только результат и сообщение — нет
идентичности Testence, ID кейса в системе управления тестированием, intent-шагов и
evidence. Инструменты, куда отчитывается большинство QA-команд, — TestRail через
`trcli`, Xray, Jenkins и GitLab — принимают JUnit и читают из него именно это:
ID кейсов из `<properties>`, результаты шагов из `testrail_result_step` TestRail, файлы
из строк `[[ATTACHMENT|path]]`. Набор тестов на Testence не мог передать им ничего из
этого.

## Рассмотренные варианты

- **Оставить только `--junitxml`.** Кода нет, ID и evidence недоступны.
- **Встроиться в JUnit-писатель pytest** (`record_property` из плагина). Снова
  привязывает отчёт к живой сессии, чего ADR-0013 и избегает, и не может положить
  замаскированные файлы evidence.
- **Экспортер ledger, как остальные.** Чистая функция прогона с той же идентичностью,
  маскировкой и политикой вложений, что у Allure.

## Решение

`testence export --to junit` пишет `junit.xml` и `attachments/<test>/…`. Один
`<testsuite>` на файл тестов; `<failure>` — продукт не согласен с тестом, `<error>` —
тест сломан или прерван, `<skipped>` — пропущен или не запускался; то же разделение, что
в Allure. Каждый `<testcase>` несёт свойства идентичности `testence.*` и Allure ID.
`@pytest.mark.testence(tms={...})` добавляет ID кейсов: `testrail` — как `test_id` (плюс
`testrail_result_step` на каждый шаг-лист и `testrail_attachment` на каждый файл),
`xray` — как `test_key` (плюс `requirements` из PlanSpec), любая другая система — как
`tms.<system>`. Те же ID попадают в Allure метками и в CTRF полем `labels`.

XML — диалект pytest по умолчанию (`junit_family=xunit1`): `junit-4.xsd` Jenkins,
кроме `<properties>` и `file` у test case, откуда перечисленные инструменты читают ID.
Если задаче нужен только результат, рекомендация прежняя — `--junitxml`.

## Последствия

JUnit становится полноценным приёмником с golden-файлами и проверкой формы. Одно и то же
имя свойства значит разное в разных инструментах (`test_id` — это `C123` у TestRail и
числовой ID задачи у Xray), поэтому файл пишется для систем, которые объявил тест, а не
для всех сразу.

## Сигнал к пересмотру

Если платформе понадобится свойство или раскладка, которых этот диалект не передаёт, для
неё заводится свой модуль-экспортер, а не флаг в этом.
