# Генераторы для авторов тестов

Команды ниже берут на себя набор, который повторяется в каждом новом наборе тестов,
чтобы автор тратил время на адреса и оракулы. Ни одна не запускает браузер и ни одна
не придумывает ожидаемых значений.

| Команда | Читает | Пишет |
|---|---|---|
| `testence plan skeleton` | markdown-файл кейсов | PlanSpec и заготовки pytest |
| `testence seed scaffold` | документ OpenAPI 3.x | фикстуры временных объектов с упорядоченной уборкой |
| `testence inventory` | журнал завершённого прогона | markdown-справочник на экран |

## `testence plan skeleton`: из кейсов — план и заготовки тестов

```bash
testence plan skeleton cases/login.md --plan specs/login.json --tests tests_e2e
testence plan skeleton cases/login.md --plan specs/login.md --tests tests_e2e --module test_login
testence plan validate specs/login.json
```

Файл кейсов — markdown одного из двух видов. Таблица с колонкой шагов и колонкой
ожидаемого результата (`#`, `Название`/`Title`, `Шаги`/`Steps`,
`Ожидаемый результат`/`Expected result`; необязательная колонка `Предусловие`):

```markdown
| # | Название | Шаги | Ожидаемый результат |
|---|----------|------|---------------------|
| 1 | Вход | 1. Открыть `/login`<br>2. Ввести «demo@example.test» в Email<br>3. Нажать «Sign in» | Отображается приветствие «signed in as demo@example.test» |
```

Или раздел на кейс с заголовком `## Кейс N — название`, `### Case N — …` или
`### N. название`, нумерованными шагами и ожидаемыми результатами в строках
`Ожидается:`/`Expected:`, списком под отдельной меткой `Ожидается:` или пунктами `→`
под шагом:

```markdown
## Кейс 2 — Пустое имя

- Предусловие: каталог пуст.

1. Нажать «Новый виджет».
   - → Открыта форма «Новый виджет»
2. Нажать «Сохранить».

Ожидается: под полем текст «Имя обязательно»
```

Что строится:

- **План.** Scenario на кейс (`case-N`), claim и обязательный `ui`-assertion на каждый
  ожидаемый результат. `statement` и `expected` — текст источника дословно. В таблице
  каждая строка `<br>` или пункт `1. … 2. …` ячейки ожидаемого результата — отдельный
  результат. Кейс без ожидаемого результата scenario не получает: он попадает в
  `open_questions` (а для плана `.md` — в его раздел `## Open questions`). Где результат
  касается сохранённых данных, поменяйте оракул assertion на `api`: генератор этого не
  знает.
- **Тесты.** Файл `test_NN_<slug>.py` на кейс или все кейсы в `--module <имя>`. У функции
  `@pytest.mark.testence(plan=…, claims=[…], case_id="case-N")`, по шагу — комментарий и
  заготовка с `intent="кейс N ш.M: …"` (`case N step M: …` для английского источника), по
  ожидаемому результату — привязанный `ex.expect_visible(…, assertion_id=…, claim_id=…)`.
  Шаг с путём становится `ex.goto`, сочетание клавиш — `ex.press`, значение в кавычках —
  значением `fill`. Адреса — никогда: каждая заготовка вызывает `TODO("…")`, который сразу
  валит шаг, пока его не заменят на `Target` из `testence explore` или снимка падения.

`--root` (по умолчанию `.`) — корень pytest: путь `plan=` в маркере считается от него.
`--id` и `--project-id` задают id плана и проекта (по умолчанию — имя файла кейсов и имя
корневого каталога).

Повторный запуск безопасен. Каждый сгенерированный файл хранит в первой строке дайджест
своего содержимого (`# testence:skeleton sha256=…`; у плана `.json` — поле
`x-testence-skeleton`). Файл, содержимое которого совпадает, обновляется по файлу кейсов;
файл, который вы правили или у которого нет маркера, получает статус `kept` и не
трогается. Поправили кейс в источнике — запустите команду ещё раз: нетронутые заготовки
подтянутся, написанные тесты останутся как есть.

С `--json` команда печатает документ `testence/plan-skeleton/1`: `format`, `plan`
(`path`, `id`, `valid`), `cases` (номер, `case_id`, название, claims, файл теста), `files`
(путь, `kind`, `status` — `created`, `updated`, `unchanged` или `kept`) и
`open_questions`. Коды выхода: 0 — записано, план проходит проверку; 2 — из файла кейсов
нельзя построить план без догадок (нет кейсов, повтор номера, нигде нет ожидаемого
результата, текст ожидания длиннее 1000 символов); 3 — план на диске правлен вручную и
больше не проходит проверку.

## `testence seed scaffold`: временные объекты и их уборка

```bash
testence seed scaffold --openapi openapi.json --out conftest_seed.py --marker "(temp)"
testence seed scaffold --openapi https://app.example/openapi.json --collections projects,posts
```

Команда читает документ OpenAPI 3.x (файл или http(s)-адрес; JSON, а YAML — если
установлен PyYAML) и пишет модуль фикстур для его коллекций. Коллекция — путь со
списочным `GET` и путём элемента под ним с `DELETE`, у схемы которого есть поле `name`,
`title`, `label` или `display_name` для маркера; остальные пути попадают в `skipped` с
причиной. `--collections` оставляет в модуле только названные (для вложенной коллекции
нужен и её родитель).

Модуль построен только на `testence_api` (`ApiClient`), без браузера, и содержит:

- `temp_name(ticket, label)` — возвращает `"<ticket> <label> <маркер>"`;
- `Sweeper` — находит помеченные объекты по имени (параметром поиска списка, если
  документ его объявляет, и всегда фильтром по маркеру), удаляет их в порядке
  `DELETE_ORDER`, повторяет `DELETE`, ответивший 409, до пяти секунд, а затем требует,
  чтобы `GET` объекта ответил 404; `assert_clean()` падает, пока что-то помеченное
  осталось;
- `temp_sweeper` — фикстура, которая в teardown убирает и утверждает «ничего не
  осталось», и фабрика `make_temp_<имя>(ticket, label, **fields)` на каждую коллекцию.

`DELETE_ORDER` ставит зависимые первыми. Коллекция зависит от другой, если в её схеме
создания или элемента есть `$ref` на схему другой (в том числе внутри `allOf` или
`items`), поле с её именем (`project_id`, `projectId`, `post_ids`) или если её путь вложен
в путь элемента другой. Цикл — ошибка: безопасного порядка нет, выберите коллекции без
него.

Модуль подключается из `conftest.py`: `pytest_plugins = ["conftest_seed"]`, дальше:

```python
def test_rename_project(ex, make_temp_project):
    project = make_temp_project("T-12", "rename", description="seeded")
    ...
```

При параллельных воркерах дайте каждому свой маркер: уборщики с общим маркером удаляют
чужие объекты. Список читается одной страницей; если помеченных объектов больше, чем
помещается на страницу, `find` уборщика нужно доработать. Повторная генерация — по
тому же правилу, что у скелета: правленый модуль получает статус `kept`.

С `--json` команда печатает документ `testence/seed-scaffold/1`: `out`, `status`
(`created`, `updated`, `unchanged`, `kept`), `marker`, `collections` (пути, поле имени,
параметр поиска, `items_key`, `parent`, `depends_on`), `delete_order` и `skipped`. Код
выхода 2 — документ не читается или безопасной уборки из него не построить.

## `testence inventory`: справочник экранов по прогону

```bash
testence inventory runs/r-local
testence inventory runs/r-local --out docs/inventory --json
```

Команда читает журнал одного прогона (`run.jsonl` и `pack.json` упавших тестов) и пишет
по markdown-файлу на страницу в `--out` (по умолчанию `docs/inventory`); имя файла — путь
страницы с шаблонами вместо id: `/projects/42/settings` становится
`projects-id-settings.md`. В каждом файле четыре генерируемых раздела:

- **Targets** — каждый Target, к которому обращались шаги на странице: роль или вид,
  имя, действия (`click` и `fill` — по записанной операции; другой шаг на Target — это
  `check`, если intent не начинается с глагола действия) и текст, который показал
  элемент;
- **API calls** — запросы браузера из записи `net` прогона (метод, путь с `{id}`,
  статусы) в тестах, которые были на этой странице, и собственные вызовы теста через
  `testence_api`, помеченные `test`;
- **Texts** — что увидели зелёные шаги `expect_*`: тосты, заголовки;
- **Traps** — шаги, которые хотя бы раз упали, с ошибкой и пометкой, стал ли тест потом
  зелёным (перезапуск, мягкая проверка или следующий прогон).

Страница шага — последний переход его теста. Журнал знает её, если intent
`goto`/`navigate` содержит URL (intent по умолчанию `open <url>` содержит), или если пакет
падения записал `page_url`; шаги до такого перехода попадают в `unknown-page.md`. Свой
intent вроде `"открыть список проектов"` прячет URL — пишите `"open /projects"` там, где
важна страница.

Повторный запуск на другом прогоне сливается с существующим файлом: прежние Target'ы,
вызовы, тексты и ловушки остаются, счётчики ловушек складываются, а уже слитый прогон не
считается дважды. Раздел, в заголовке которого стоит `<!-- manual -->`, — ваш и
сохраняется дословно:

```markdown
## Заметки <!-- manual -->

Кнопка Save неактивна, пока имя не изменено.
```

Состояние слияния хранится в комментарии `<!-- testence:inventory … -->` в конце файла —
не удаляйте его. С `--json` команда печатает документ `testence/inventory/1`: `run_dir`,
`out` и `pages` (страница, путь, статус, число Target'ов, вызовов API, текстов, ловушек и
ручных разделов). Код выхода 2 — каталог прогона не читается.
