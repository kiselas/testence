## Контуры продукта

**Контур управления агентом** превращает намерение человека в планы, тестовый код,
вердикты и предложения сопровождения. Процесс задаётся переносимыми skills и
инструкциями репозитория; CLI/MCP предоставляет ограниченные операции. Этот контур
может использовать LLM и должен оставаться заменяемым.

**Контур детерминированной верификации** отвечает за браузерное исполнение, API-oracles
и журнал событий. При обычном воспроизведении он не зависит от вызова модели. Это
источник истины о том, что выполнялось и что прошло.

**Контур доверия и управления** охватывает оба предыдущих: идентификаторы
трассируемости, схемы, редактирование, хранение, разрешения, review предложений и
provenance. Вывод агента становится доверенным только после прохождения одного из этих
явных контрактов.

Целевой публичный цикл описан в [agent-workflow.md](agent-workflow.md), границы продукта —
в [product-positioning.md](product-positioning.md).

## Слои

Направление зависимостей: верхние слои зависят от нижних, но не наоборот и не через
соседний слой вверх.

| Слой | Модуль | Ответственность | Что может импортировать |
|---|---|---|---|
| тестовые сценарии | репозиторий проекта | по 5–15 строк DSL с намерением | проектный ActionMap |
| ActionMap | репозиторий проекта | шаги приложения, селекторы, обход продуктовых ловушек, oracles | `testence.dsl`, `testence.oracle`, адаптеры |
| DSL | `testence.dsl` | обёртка шага: намерение, время, fingerprint и события | `testence.engine`, `testence.evidence` |
| адаптеры | `testence.adapters` | контракты Auth/Seed, реализуемые в проекте | `testence.engine` |
| триаж | `testence.triage` | сборка pack и контракт таксономии вердиктов | engine, evidence |
| engine | `testence.engine` | единственный модуль, импортирующий Playwright | playwright |
| evidence | `testence.evidence` | writer для run.jsonl, схема и бюджеты | kernels, stdlib |
| представления | `testence.report`, `testence.metrics`, `testence.cli` | рендеринг поверх журнала | evidence, kernels |
| kernels | `testence.kernels` | чистые CPU-функции за версионированным ABI; заменяемы native backend | только stdlib |

Правила, сохраняющие честность фасада:

- Ничто вне `testence/engine/` не импортирует Playwright и не работает с его типами
  (`Target` и `NetRecord` принадлежат Testence). Сейчас это проверяется review, с
  ростом репозитория появится lint-rule.
- DSL-код никогда не делает sleep: ожидание принадлежит engine (auto-wait) или явным
  условиям `expect_*`.
- Всё, что узнаёт запуск, проходит через `EvidenceWriter`; побочных логов нет.
- Нагруженные чистые CPU-функции находятся в `testence.kernels` — простые данные
  на входе и выходе, без I/O. Благодаря этому они механически переносимы в native
  backend; см. [kernels.md](kernels.md). I/O-код, включая writer и engine, туда не
  попадает.

Внутри контура верификации есть два профиля производительности. **Путь управления**
(engine/DSL/pytest) ограничен I/O: шаг ждёт один CDP round-trip, поэтому выбор языка
здесь почти не влияет на скорость. **Путь анализа** — разбор журнала, diff snapshot и
оценка кандидатов — ограничен CPU и скрыт за kernel ABI. Оптимизировать нужно только
второй путь и лишь после пересечения порога в `bench/kernels.py`.

## Поток исполнения одного теста

1. Pytest lifecycle hook публикует `test.start` для каждого selected test, включая
   тесты без `ex`; fixture при использовании сбрасывает browser capture.
2. Каждый вызов `Actions`: `step.start` с намерением и целью → действие engine с
   auto-wait → `step.end` с длительностью и fingerprint на зелёном пути.
3. Точки oracle: проверки вида `save_and_verify` публикуют события `oracle`;
   расхождение выбрасывает исключение и завершает шаг ошибкой.
4. При падении `assemble_pack` захватывает ARIA, network, console, oracle и
   `browser.json`, если browser fixture создан, и публикует `pack`; источником
   execution outcome остаются pytest phase reports.
5. После teardown lifecycle hook публикует canonical `test.end`. Перед export reader
   восстанавливает missing terminal и selected cases, которые не начали.

## Режимы

| Режим | Как работает | Применение |
|---|---|---|
| локальный full stack | engine запускает системный Chrome | разработка, самый быстрый цикл |
| подключение к существующему браузеру | `--testence-cdp http://127.0.0.1:9222` подключает Chrome, в который уже вошёл разработчик | локальное исследование общих окружений |
| CI | headed-режим под `xvfb-run`, артефакты `when: always`, триаж только по pack | регрессия с нулевой стоимостью LLM |

## Граница реализации

| Возможность | Состояние |
|---|---|
| исполнение pytest/DSL/Playwright | реализовано |
| изоляция evidence по тестам и исполнение xdist | реализовано |
| версионированный журнал, ограниченные pack и HTML-отчёты | реализовано |
| экспорт Allure и CTRF из журнала | реализовано |
| примитивы heal proposal на fingerprints | реализовано |
| переносимые agent skills и bootstrap проекта | предстоит реализовать |
| PlanSpec и трассируемость claim → pytest → ledger → pack/report | реализовано |
| verdict schema, pack template и CLI-валидация | реализовано |
| управляемое сохранение verdict и MCP для агента | предстоит реализовать |
| систематическое редактирование evidence и permission policy репозитория | блокер P0 |
| intent cache или escape hatch для model-driven authoring | позже, только opt-in |

Работающий runner ещё не означает законченную архитектуру. Для готовности публичной
альфы поддерживаемый coding agent должен пройти весь workflow, а каждый переход должен
оставаться проверяемым.
